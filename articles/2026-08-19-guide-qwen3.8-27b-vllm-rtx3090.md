# Guide: Qwen3.8-27B at ~100 tok/s on one RTX 3090 with vLLM

_2026-08-19 · companion to [the measurements article](2026-08-19-qwen3.8-27b-rtx3090-llamacpp-vs-vllm.md)_

**End state: Qwen3.8-27B answering at ~98 tok/s, eight requests in parallel,
131k context, on one 24 GB card — in under an hour, most of it downloads.**
This is the [syv-ai/qwen38-27b-rtx3090](https://github.com/syv-ai/qwen38-27b-rtx3090)
setup exactly as I ran it, plus the six things that bit me which its README
doesn't mention. Follow it top to bottom on a 24 GB Ampere-or-newer card.

## 0. Before anything: two checks

```bash
nvidia-smi --query-gpu=power.limit,power.default_limit --format=csv
free -h
```

- **Power limit.** Mine was quietly capped at 200 W — worth −40% throughput.
  `sudo nvidia-smi -pl 350` (or your card's default) is the cheapest speedup
  in this whole guide.
- **RAM.** You need ~15 GB of _available_ RAM during model load and the prep
  steps. If a llama.cpp server with a big `--cache-ram` (or anything else
  fat) is resident, stop it first — my first two attempts were OOM-killed and
  took my desktop session's Firefox with them.

## 1. Clone + venv

Python 3.12 (not newer — the patches target vLLM 0.27.1's tree):

```bash
git clone https://github.com/syv-ai/qwen38-27b-rtx3090 ~/qwen-serving
cd ~/qwen-serving
uv venv --python 3.12 venv
uv pip install --python venv/bin/python "vllm==0.27.1" huggingface_hub hf_transfer ninja
```

Pin vLLM to **0.27.1** — the eight patches are written against it and a newer
wheel will half-apply.

## 2. Download the model (~19.5 GB)

```bash
HF_HUB_ENABLE_HF_TRANSFER=1 venv/bin/hf download \
  dbirks/Qwen3.8-27B-W4A16-AutoRound \
  --local-dir models/Qwen3.8-27B-W4A16-AutoRound
```

## 3. Requantize + fetch the fast variant

These rewrite the checkpoint in place (CPU-only, a few minutes each). On a
≤32 GiB-RAM box, run them inside a memory-capped scope so a spike kills the
script and not your desktop:

```bash
M=models/Qwen3.8-27B-W4A16-AutoRound
run() { systemd-run --user --scope -p MemoryMax=16G -p MemorySwapMax=16G "$@"; }
run venv/bin/python quant_lm_head.py $M
run venv/bin/python quant_embed.py   $M
run venv/bin/python quant_mtp.py     $M
run venv/bin/python build_draft_vocab.py $M --ids draft_vocab_ids.json
run venv/bin/python fetch_fast_variant.py
```

## 4. Patch vLLM, make a key, verify

```bash
for p in patches/*.patch; do
  patch -p1 -d venv/lib/python3.12/site-packages/vllm < "$p"
done
openssl rand -hex 24 > api_key.txt
bash verify.sh --no-server     # must end: verify: OK (0 failures)
```

`verify.sh` checks every patch and every requant step individually — trust it
over your memory of what ran.

## 5. Launch

The GPU must be **idle** at launch (the repo warns a dirty start silently
costs ~25%; separately, vLLM refuses to start if the free-VRAM check fails).
A desktop compositor holding ~2 GB is fine but costs you headroom — I ran:

```bash
CTX=long GPU_UTIL=0.90 MAX_LEN=131072 bash single-user/start_qwen.sh
```

- `CTX=long` = 131–150k context on fp8 KV. On my card it matched the 64k
  `CTX=fast` mode single-stream and _beat_ it at concurrency — take the
  context.
- Headless box with the full card free? Use the script's defaults
  (`GPU_UTIL=0.93`, 150k).
- First start takes minutes (torch.compile, CUDA graphs, flashinfer JIT).

**Vision:** the script passes `--language-model-only`, so images are refused
with `At most 0 image(s)`. The quant's vision tower is intact — to serve
images, launch plain `vllm serve` with the script's other flags minus that
one (drop `MAX_LEN` to ~64k to make VRAM room for the tower).

## 6. Benchmark it properly

```bash
uv pip install --python venv/bin/python "vllm[bench]==0.27.1"   # pandas etc.
bash bench/run_benchmarks.sh single
bash bench/run_benchmarks.sh single   # keep THIS one; run 1 reads 30-50% low (JIT)
```

Two rules that saved me from publishing wrong numbers:

- **Bench the engine standalone.** My first llama.cpp comparison ran through
  my model proxy while an agent was chatting; the interleaved traffic halved
  one run. (The same `vllm bench serve` harness works against llama-server
  too — it's just an OpenAI-compatible client — so both engines can share one
  protocol.)
- **Run twice, keep the second.** The repo says so, and the warmup effect is
  real.

## What you should see (RTX 3090)

| power limit            | 1 stream    | 8 streams total |
| ---------------------- | ----------- | --------------- |
| 200 W (a quiet card)   | 64–65 tok/s | 245             |
| 250 W (repo's numbers) | 83–87 tok/s | ~328            |
| 350 W (mine)           | 92–98 tok/s | 387–409         |

If you're well under that: check the power limit (step 0), check the GPU was
idle at launch (step 5), and re-run `verify.sh` (step 4).
